# 模型与权限

Ennote 不绑定任何一家模型服务：只要兼容 OpenAI 风格的接口就能接。

## 配置 Provider

设置 → 模型 → 新建 Provider，需要填三样：

| 字段 | 说明 |
|---|---|
| Base URL | 例如 `https://api.openai.com/v1`，也可以是本机的 Ollama / LM Studio |
| API Key | 保存在 `~/.ennote/config/`，文件权限 `0600`，不会写进日志 |
| 模型列表 | 手动填写或拉取该 Provider 提供的模型 id |

本机推理服务是允许的：Provider 探测对 loopback 地址放行。但**抓取网页内容**的工具（web_fetch）
对 loopback 与私有网段是**拦截**的——它抓的是不可信内容，不能让它反过来探测你本机的服务。

## 选择模型

每个 Session 独立选择模型与思考深度（thinking effort）。也可以在 Project 里设默认值，
新 Session 继承。

一次 Run 冻结的配置会记录在快照里，所以事后能查到"这条回答是哪个模型、在什么配置下产生的"。

## 三种权限模式

三种模式只在一件事上不同：**遇到非只读工具（写文件、执行命令、联网抓取、委派）时怎么办**。
界面上的名字就是这件事的答案，括号里是配置文件实际存的值——同一个模式的两个写法。

| 模式 | 遇到非只读工具 | 适合 |
|---|---|---|
| 只读（`discuss`） | 直接拒绝 | 只想让它看和讨论 |
| 逐项审批（`ask`） | 逐个请求你批准 | 默认推荐 |
| 全部放行（`auto`） | 直接执行 | 你已经信任这个任务 |

模式在输入框下方的运行配置条里随时可切；切换只影响之后的工具调用，不会重放已经发生的事。

## Role 的权限天花板

委派给一个 Role（角色）时，子 Run 的权限取**两者中更严的那个**：

```
子 Run 权限 = min(父 Run 当前模式, Role 声明的 permission ceiling)
```

也就是说：父 Run 在逐项审批（`ask`）、Role 声明全部放行（`auto`），子 Run 仍然是 `ask`。
反过来，Role 声明只读（`discuss`）时，即使在 `auto` 的父 Run 下，子 Run 也只有只读权限。
Role 编辑器里的 Permission ceiling 下拉就是这三个值，按严格程度排列。

对于无法折算成内建模式的情况（例如 Role 用的是受限策略），子 Run 会被钉到最严的内建模式，
而不是继承宽松的那一侧 —— 权限比较不出来时，往严格的方向失败。

## 审批与委派准入

两处都需要你点头：

- **工具审批**：一次工具调用超出当前模式允许的范围
- **委派准入**：一次委派要花你的额度/时间时，可以要求先批准再放行

审批决策会写进事件流，事后可追溯：谁批的、什么时候、批的是什么参数。

## 沙箱

默认模式是 `bwrap`（bubblewrap），**所有平台一致**：文件系统隔离，只有工作区可写。

!!! warning "macOS 上需要先装 bubblewrap 或改用降级模式"
    macOS 不自带 `bwrap`。缺少它时，执行类工具会直接报错
    （`bubblewrap is required for sandbox mode bwrap`），而不是静默降级。
    在 macOS 上要么装 bubblewrap，要么显式设置 `ENNOTE_SANDBOX=none` 使用降级模式。

降级模式（`ENNOTE_SANDBOX=none`）下，Worker 会对 shell 命令做静态分析，拒绝一切可能拼出受保护
路径的写法（未加引号的通配符、花括号展开、变量展开、命令替换、`$'...'` 等），并拒绝访问
`~/.ennote`。但它毕竟是静态分析：`sh -c "$(cat x)"` 这类间接执行只有真正的沙箱能挡住。
